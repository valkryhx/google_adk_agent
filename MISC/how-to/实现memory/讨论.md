1. Ripgrep 的天生强项就是“跨文件并发搜索”

2. 赋予 Agent 极低成本的“时间过滤”能力（时序数据库思维）
把日期写在文件名里，实际上是给文件系统做了一层时间倒排索引。
如果把一年的对话都塞进一个文件，Ciri 想查“上周二我们聊了什么”，它必须写极其复杂的正则表达式去匹配文件里的时间戳前缀。

3. 防止 LLM 的上下文窗口（Context Window）爆炸
这是目前很多单体 Agent 最容易踩的坑。如果一个复杂的项目 Session 持续了半年，单文件大小可能会膨胀到几 MB。
当 Ciri 某天想要调用 read_memory (也就是 File Edit 的 view 命令) 去粗略翻阅这个文件的开头时，超大的文件不仅会造成文件系统读取卡顿，如果 Agent 不小心读取了过多的行数，会直接把 LLM 的 Token 撑爆导致进程崩溃。
按天切分天然起到了**“内存分页（Paging）”**的保护作用，让 Agent 每次读取的数据量被物理上限锁死。

你拥有访问完整历史记忆档案的能力。所有的对话和动作记录都以 Markdown 文件的形式保存在 `memory_archive/` 目录下。

## 黄金检索法则：两步走战略 (L0 -> L2)

你**绝不能**盲目猜测历史，也**绝不能**一次性读取整个文件。必须严格遵循“先广度扫描，后深度阅读”的工作流：

### 第一步：L0 广度扫描 (`search_memory`)
使用底层的 `ripgrep` 引擎进行全局正则表达式扫街，以获取目标信息所在的【文件名】和【精确行号】。

* **强制要求 1：必须携带上下文参数**。在构建 `ripgrep` 查询时，**务必**在参数中包含 `-C 2`（或 `-B 2`），以便在返回结果中看到匹配行的前后两行，从而判断该行是否是你需要的线索。
* **强制要求 2：精准收缩范围**。如果已知时间或节点，**务必**使用 `-g` 参数过滤文件名。例如：`-g "2026-03-*_swarm_*.md"` 可以只搜索 3 月份所有 Worker 节点的记录。

### 第二步：L2 深度精读 (`read_memory`)
当第一步为你提供了带有上下文的线索，并让你锁定了特定的文件和行号后，你必须调用此工具。

* **操作指南**：传入 `file_path`，并指定 `start_line` 和 `end_line`（建议读取目标行上下的 20-40 行）。
* **目的**：获取完整的报错堆栈、长段的 JSON 参数或连续的对话逻辑。

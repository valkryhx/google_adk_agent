# Kairos 本次测试设计说明

> 适用提交：`97c380a test(kairos): add staged workflow live verification`
> 目标读者：继续维护本仓库的人类开发者与后续 agent

## 1. 这批测试代码是做什么的

这次提交新增/强化的测试，不是单纯为了把覆盖率数字抬高，而是为了把 **KAIROS 的演示故事线** 变成可重复验证的工程事实。

核心要验证的不是“某个函数返回了什么”，而是下面这条完整能力链：

1. Dex 能真实创建和执行后台任务
2. KAIROS 能把 Dex task 作为 handoff 对象持续跟踪
3. 多个 phase-1 任务可以并行收敛，而不是只支持单任务 smoke case
4. 在 phase-1 收敛后，report 阶段可以重新进入 handoff 并最终完成
5. 最终业务产物会真实落盘到 `demo_outputs/`
6. KAIROS 最近事件、tracked task 状态、最终 idle 收敛都能被观察到
7. 这些验证既能在纯测试环境跑，也能在“服务已启动”的 live HTTP 环境跑

一句话说：

> 这批测试把“KAIROS 是 Dex 之上的协调层”从口头叙事，变成了运行时、集成层、服务层三层都有证据的可回归能力。

---

## 2. 为什么需要这批测试

在这次提交之前，代码库已经能证明以下事情：

- Dex 基础任务模型可工作
- KAIROS 能注册 handoff 并观察单个任务
- 前端能显示 `Tracked Dex Tasks` 和 `recent_events`

但还缺三类关键证据：

### 2.1 缺少 staged workflow 证据
原先更像是在证明：
- 一个任务可以被跟踪
- 一个任务完成后会消失

这不足以证明：
- phase-1 并行任务能逐步收敛
- report 阶段能在 phase-1 之后重新接管流程
- KAIROS 管的是 workflow，而不是单个任务状态

### 2.2 缺少真实 Dex 子进程证据
原先大量测试使用 fake bridge / fake snapshot，这对 runtime 逻辑很好，但不能证明：
- `.dex/tasks/<user>/*.json` 的真实状态变化能被 KAIROS 正确消费
- Dex 的真实后台子进程执行结果能反映到 KAIROS 事件中

### 2.3 缺少服务层 + 产物层证据
原先没有一条稳定的回归，能同时说明：
- 服务已启动
- session 与 Kairos API 正常
- Dex handoff 真实注册
- demo_outputs 真实落盘
- report.json 内容正确

而这正是 live demo 对工程观众最关键的说服力来源。

## 3. 这次测试总体采用了怎样的验证设计

本次测试是分层设计的，不是只靠一条大而全的 E2E。

### 第 1 层：运行时语义验证
代表文件：
- `tests/kairos/test_runtime.py`

目标：
- 验证 KAIROS runtime 的状态机是否符合预期

特点：
- 快
- 稳定
- 不依赖真实服务
- 适合验证 `handoff -> idle -> handoff -> idle` 这类状态转换语义

### 第 2 层：真实 Dex/Kairos 集成验证
代表文件：
- `tests/dex/test_tools.py`

目标：
- 验证真实 Dex 任务文件、真实子进程执行与 Kairos polling 的结合是否成立

特点：
- 不走 HTTP
- 但使用真实 `DexManager` / `KairosDexBridge` / `KairosRuntime`
- 能证明不是 fake 数据自娱自乐

### 第 3 层：服务启动后的 live HTTP 验证
代表文件：
- `tests/kairos/live_http_kairos_demo_outputs_regression.py`
- `tests/kairos/test_live_http_kairos_demo_outputs_regression.py`

目标：
- 验证“已启动服务”的真实 demo 流程

特点：
- 依赖 `http://127.0.0.1:8000`
- 通过真实 API 创建 session / 启动 KAIROS / 注册 handoff / 查询状态
- 最终验证 `demo_outputs/*.json` 和 `report.json`

��样的三层结构有几个好处：

1. **定位快**：runtime 挂了先看状态机，integration 挂了看 Dex/Kairos 边界，live 挂了看服务层/环境层
2. **成本分层**：不是每次都跑最重的 live 验证
3. **适合 agent 扩展**：后续 agent 可以明确知道“改某层逻辑，优先补哪一层测试”

## 4. 各个新增测试分别验证什么

## 4.1 `tests/kairos/test_runtime.py`
### 关键新增用例
- `test_multi_stage_dex_workflow_keeps_parallel_tasks_then_converges_to_report`

### 它验证什么
它验证的是 **workflow 语义**，不是文件系统或服务 API：

#### phase-1
- 三个 tracked task 已存在：`sales / traffic / quality`
- 其中一个先完成，另外两个仍在运行
- KAIROS 仍保持 `HANDOFF`

#### phase-1 收敛
- 剩余两个任务完成后
- tracked 列表清空
- mode 回到 `IDLE`

#### report 阶段
- 再注册 `report`
- KAIROS 再次进入 `HANDOFF`
- report 完成后再次回到 `IDLE`

#### event 可观察性
- `recent_events` 中能看到：
  - `sales ready`
  - `traffic ready`
  - `quality ready`
  - `report ready: 3 inputs merged`

### 为什么这个测试重要
因为它第一次明确把“单任务 handoff”提升成了“多阶段 workflow handoff”。

如果以后有人修改 runtime，把 phase-1 收敛逻辑、report 阶段重入逻辑改坏，这条测试会第一时间告诉你：

> 你破坏的不是某个局部函数，而是 KAIROS 作为协调层的核心叙事。

---

## 4.2 `tests/dex/test_tools.py`
### 关键新增用例
- `test_kairos_runtime_polls_real_dex_tasks_until_report_stage_finishes`

### 它验证什么
这条测试不是 fake bridge，而是：

1. 用 `DexManager` 真实创建 task
2. 用 `dex_start_task` 真实启动后台 Python 子进程
3. 让 Dex 真实写入 `.dex/tasks/...json`
4. 用 `KairosDexBridge` 读取真实 task 文件
5. 用 `KairosRuntime.tick_once()` 真实轮询
6. 验证 report 阶段完成后，KAIROS 收敛到 `idle`

### 为什么这个测试重要
这条测试的价值在于它跨过了一个关键边界：

> 不再只是“runtime 看 fake snapshot”，而是“runtime 真正在消费 Dex 任务文件”。

所以如果以后有人改动：
- Dex 任务文件结构
- `result_summary` 生成方式
- `KairosDexBridge` 字段映射
- `tick_once()` 的完成判断

这条测试都能起到防回归作用。

---

## 4.3 `tests/kairos/live_http_kairos_demo_outputs_regression.py`
### 它验证什么
这是本次最接近演示现场的验证脚本。

它做了这些事情：

1. 要求服务已经启动在 `:8000`
2. 通过 HTTP 创建 session
3. 通过 HTTP 启动 KAIROS
4. 真实创建 phase-1 三个 Dex task
5. 通过 HTTP 把这些任务注册给当前 session 的 KAIROS
6. 真实启动本地后台子进程执行设计文档里的 Python 命令
7. 等待 `.dex/tasks/user_001/*.json` 进入 `completed`
8. 等待 KAIROS 从 `handoff` 收敛到 `idle`
9. 重复上述过程完成 report 阶段
10. 最终验证：
   - `demo_outputs/sales.json`
   - `demo_outputs/traffic.json`
   - `demo_outputs/quality.json`
   - `demo_outputs/report.json`
11. 检查 `report.json` 的 summary 数值正确
12. 检查 `recent_events` 中确实留下四个完成事件

### 为什么它很重要
这条脚本验证的是“演示故事是否真的成立”。

它不像纯单测那样只看函数返回值，而是回答：

- 现场启动服务后，这套 demo 到底能不能跑通？
- 产物能不能落盘？
- KAIROS 事件能不能留下？
- report 阶段是不是实际基于 phase-1 的文件输出？

这条脚本基本就是给人类演示者和未来 agent 的“可执行真相源”。

## 4.4 `tests/kairos/test_live_http_kairos_demo_outputs_regression.py`
### 它验证什么
这是一层 pytest 包装。

它的作用不是增加新逻辑，而是让上面的 live 脚本：
- 能被 `pytest` 统一调度
- 能进入 CI / 本地回归命��集合
- 能与其他测试一起执行与报告

### 为什么要保留这层包装
因为很多后续自动化系统、agent 工作流、测试面板都默认消费 pytest。

如果只有一个裸 Python 脚本，虽然人能跑，但自动化体系不好接入。

## 5. 这批测试是如何取舍验证边界的

这是后续开发最需要理解的部分。

### 5.1 为什么 live 脚本仍然保留 HTTP，但没有让 Dex create/start 也走 chat agent
因为我们在实践中已经观察到：
- `/api/chat` 是 NDJSON 流
- 会带历史上下文
- 对“只想稳定拿到任务 id”的场景不够稳
- 多轮连续调用时容易让测试 harness 自己变复杂

因此当前设计做了一个有意识的边界切分：

#### 保留 HTTP 的部分
- 创建 session
- 启动 KAIROS
- 注册 handoff
- 查询 KAIROS 状态

#### 直接调用 Python 的部分
- Dex task 创建
- Dex task 启动

这样设计的意义是：
- **保留 KAIROS 服务层的真实性**
- **避免 chat agent 层让回归测试不稳定**

换句话说，这是一种“为演示能力做服务层验证，而不是为大模型对话行为做验证”的刻意取舍。

如果未来你要测试 agent 自己是否会正确选择 dex 工具，那应该另开一类测试，不要和这里混在一起。

---

## 5.2 为什么 `_fetch_dex_task()` 要容忍空文件/半写入
我们在复跑 live pytest 时观察到一个偶发竞态：
- 后台子进程正在写 `.dex/tasks/<id>.json`
- 测试线程正好读到空文件或半写入状态
- 直接 `json.loads()` 会抛异常

所以这里故意把 `None / 空文本 / JSONDecodeError` 视为“文件尚未稳定”，继续轮询。

这不是掩盖问题，而是正确地承认：

> live 环境里的文件读写是并发事件，测试不应该假设文件永远原子可读。

后续如果你再写任何基于 `.dex/tasks/*.json` 的 live 轮询测试，应该沿用这个模式。

---

## 6. 这批测试没有验证什么

要指导后续开发，必须明确空白区。

这次测试**没有**重点验证：

1. 前端浏览器真实 DOM 操作
   - 当前是通过状态/API/产物间接证明
   - 不是 Playwright 级别 UI 端到端

2. 大模型是否会在自然语言提示下稳定选对 dex 工具
   - 当前 live 脚本不依赖模型推理稳定性
   - 它验证的是系统能力，不是模型行为稳定性

3. 复杂失败恢复策略
   - 比如 phase-1 某个任务失败后自动重试、部分推进、补偿逻辑
   - 当前只覆盖成功主路径为主

4. 长时间运行/高并发
   - 当前是 demo 级 workflow
   - 不是压力测试

这意味着后续开发如果要增强这些方向，应该新增新的测试层，而不是硬往这批测试里塞。

## 8. 推荐的后续扩展方向

如果后续继续开发，建议按下面顺序补强：

### 方向 1：失败路径验证
建议新增：
- phase-1 某个任务失败
- report 因缺文件失败
- KAIROS recent_events 正确记录失败原因
- tracked 列表正确清空或保留待处理任务

### 方向 2：前端 live E2E
建议新增：
- 打开页面
- 启动 KAIROS
- 注册 task
- 检查 `Tracked Dex Tasks` 面板文本
- 检查最终 `report.json` 和 recent events

### 方向 3：agent 驱动的真实演示验证
建议单独开一类测试，不要污染当前 live 脚本：
- 用自然语言让 agent 自己选择 dex 工具
- 验证 agent 是否真的能稳定构造 phase-1 + report 流程

## 9. 给未来 agent 的开发约束

如果未来 agent 要继续扩展这里的测试，请遵守：

1. **不要把所有验证都堆到最重的 live 测试里**
   - 先判断是 runtime 层、integration 层还是 service/live 层问题

2. **改 live 测试时，优先保证稳定性而不是追求“最像人类点击”**
   - 这里只验证系统能力，不主测 agent 对话表现

3. **任何涉及 `.dex/tasks/*.json` 的 live 轮询，都必须考虑并发读写窗口**
   - 不能假设文件永远原子可读

4. **如果修改 demo 业务值（128/3421/pass），必须同步更新：**
   - 设计文档
   - live HTTP 回归断言
   - 相关说明文档

5. **如果将来把 Dex create/start 再改回走 HTTP/chat，必须先解决 NDJSON 流解析稳定性问题**
   - 否则不要为了“更像真实对话”而牺牲回归稳定性

## 10. 最终总结

这次新增的测试设计，本质上是在回答三个问题：

### 问题 1：KAIROS 真的是 workflow 协调层吗？
回答方式：
- `tests/kairos/test_runtime.py`

### 问题 2：KAIROS 真能消费真实 Dex 任务，而不是 fake 数据吗？
回答方式：
- `tests/dex/test_tools.py`
- `tests/kairos/test_dex_bridge.py`

### 问题 3：启动服务后，这个 live demo 真能落地生成业务产物吗？
回答方式：
- `tests/kairos/live_http_kairos_demo_outputs_regression.py`
- `tests/kairos/test_live_http_kairos_demo_outputs_regression.py`

因此，这批测试的真正价值不是“多了几个 pass”，而是：

> 它们把 KAIROS phase-2 的演示能力，从“看起来能讲通”，提升到了“可以被重复验证、可以被后续 agent 安全扩展、也能指导人类继续开发”的状态。

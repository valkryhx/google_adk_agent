Claude Code 源码泄露技术探索与架构分析报告

文档背景：2026年3月31日，Anthropic 在 npm 发布 Claude Code v2.1.88 版本时，因构建配置失误将包含完整源码映射的 .map 文件（cli.js.map）打包发布，导致约 51.2 万行 TypeScript 底层代码曝光。本报告基于该泄露源码的反编译结果，针对其多智能体架构、状态管理、长程规划及工程实现细节进行技术梳理。

1. Claude Code 的多智能体设计、复刻项目及未来路线图

提问： Claude Code 的多智能体设计是怎么设计的？有没有 GitHub 项目解读？以及下一步的计划和路线图是什么？

解答：

多智能体设计： 源码显示系统并未单一依赖大模型的原生上下文，而是构建了一个 Agent Harness（智能体挂载框架）。核心包含：

Coordinator Mode（协调器模式）：将主进程转变为任务拆解与调度中心，通过 Unix Domain Sockets (UDS) 或 XML 消息总线管理多个并发的 Worker 进程。

Kairos：后台常驻守护进程，负责自主休眠与跨会话记忆整合。

Auto Mode Classifier：轻量级的权限分类模型，用于静默审批非破坏性工具的调用，减少人机交互摩擦。

开源解读与复刻项目： 社区已出现多个净室分析与备份项目。代表性的包括备份镜像（如 tanbiralam/claude-code）、探索隐藏功能开关的魔改版（如 leaked-claude-code/leaked-claude-code），以及使用 Rust 等语言重写核心架构的项目（如 Kuberwastaken/claude-code）。

路线图与隐藏功能： 源码中包含了 44 个未激活的 Feature Flags（功能开关）。暴露的路线图包括：下一代模型代号（Numbat、预留的 Opus 4.7/Sonnet 4.8）；名为 Buddy 的游戏化宠物伴侣系统；针对企业环境隐藏 AI 生成特征的 Undercover Mode（卧底模式）；以及长程自治模式 KAIROS 和云端超长程规划模式 ULTRAPLAN。

2. Coordinator 模式的具体实现机制

提问： 详细讲讲 Claude Code 的 Coordinator Mode 是怎么运作的。

解答：
Coordinator 模式的核心是将系统的运行流从“单一的对话循环”转变为“团队编排流”。其技术实现包含以下组件与阶段：

任务队列与 DAG 依赖图： 接收复杂目标后，Coordinator 内部生成有向无环图（DAG），明确子任务之间的并行与串行拓扑依赖。

生命周期与通信： 通过 AgentTool 等工具动态派生（Spawn）子智能体，子节点间通过 MessageBus（消息总线）和共享内存（Shared Memory）传递状态。

四阶段工作流：

Research（研究）： 多个 Worker 并行使用 Grep/AST 工具检索代码库。

Synthesis（综合）： Coordinator 汇总 Worker 的线索，生成代码修改规范（Specs）。

Implementation（实现）： 派发规范至 Worker 并发修改文件，由 Coordinator 处理合并冲突。

Verification（验证）： 调度测试 Worker 执行编译脚本，根据输出判断是否需返工。

3. ULTRAPLAN 长程规划模式与云端容器运行时 (CCR)

提问： ULTRAPLAN 模式的具体实现是怎么做的？它和本地执行有什么区别？云端如何获取本地的项目环境信息？

解答：
ULTRAPLAN 被设计为基于云端容器的超长程异步规划器。其核心解决的是本地 API 调用超时和复杂任务导致的上下文熵增问题。

云端容器运行时 (CCR)： 触发该模式后，规划任务被卸载（Offload）到云端的隔离容器中运行（源码注释指向未发布的 Opus 4.6 算力节点）。该环境赋予模型最高 30 分钟的异步执行预算，免于常规网关的 HTTP 429 或 504 超时限制。

上下文投影机制： 云端容器并不全量复制本地硬盘。本地 CLI 会先生成项目的语义拓扑图（目录结构、类/函数签名）传至云端。在云端推演时，通过内部集成的 MCP (Model Context Protocol) 协议，按需（On-demand）向本地请求读取特定文件的具体内容，同时在内存中模拟项目的依赖版本。

蓝图回传： 云端模型在此期间不修改实际业务代码，仅进行架构推演，最终生成一份包含精确步骤和依赖关系的文件修改蓝图（Blueprint），并通过内部的 /teleport 命令下发至本地，交由 Coordinator 统筹执行。

与本地执行的区别： 本地执行为同步阻塞，受限于超时断开，且一边规划一边修改；ULTRAPLAN 为完全异步（Fire & Forget），云端节点有状态持久化（Stateful），输出产物为纯粹的工程图纸。

4. KAIROS 模式、运行机制及对垂直智能体的借鉴

提问： KAIROS 模式是怎么实现的？为何要实现这个模式？对开发自己的垂直领域智能体有什么指导意义？

解答：
KAIROS 是一个完全托管的系统级后台守护进程（Daemon）。

工程实现：

Tick Loop：摒弃了等待用户输入的阻塞逻辑，通过后台心跳循环主动唤醒系统。

SleepTool：系统根据任务队列和资源消耗，自主决定休眠或唤醒时机。

异步阻塞预算：执行外部编译或网络请求等操作时，限制 15 秒阻塞时长，超时则挂起（Backgrounding），防止主进程死锁。

事件驱动：支持绑定 Cron 定时任务或 Webhooks。

设计动机： 解决单次执行的上下文遗忘问题，实现从被动响应工具到主动巡检、优化的后台系统的范式转变。

对垂直智能体的借鉴： 开发特定领域的 Agent（如网络优化智能体）时，可引入 Tick Loop 实现常驻监控；深度集成 MCP 协议实现状态与推理的解耦；对所有耗时的外部调用强制设定短时阻塞预算，并走异步回调。

5. autoDream (记忆固化) 与 RAG (检索增强) 替代方案

提问： autoDream 模式具体执行什么工作？源码中有没有提到 RAG 或检索机制？

解答：
autoDream 是一种长程记忆的离线异步压缩与蒸馏机制。

工作流： 在系统空闲或夜间，后台进程读取当天的只追加（Append-only）操作日志。执行降噪与修剪，丢弃导致报错的试错分支；随后将成功的经验压缩为“工程事实（Engineering Facts）”或架构规则，并将其覆写至本地的 Markdown 或 JSON 配置文件中。

经验分级注入： 提炼出的高优系统规则会被静态注入到次日的 System Prompt 初始化中；而大量的具体避坑指南则作为文本留存。

关于 RAG 与检索机制的澄清： 源码显示，系统完全抛弃了传统的向量数据库（Vector DB）和基于 Embedding 的语义相似度检索。因为代码的语义相似度通常不代表逻辑相关性。

替代方案（工具链检索）： 系统向模型注册了 GrepTool（底层为 ripgrep 进行正则/关键字检索）、GlobTool（文件树探索）和 ASTSearchTool（抽象语法树分析）。当模型需要回忆时，它通过调用这些精准的字符串和语法检索工具，在纯文本的日志和代码库中寻找信息。

6. 四级上下文压缩策略

提问： 泄露源码中四个级别的上下文压缩工具是怎么处理的？

解答：
为了防止长会话导致 Token 爆表，系统实现了一套从物理层到逻辑层的递进式压缩流水线：

本地探针 (Token Metering)： 在发送请求前，本地代码实时计算 Payload 体积。在达到设定的软门限（如总窗口 80%）之前，不做任何干预。

工具输出截断 (Heuristic Output Truncation)： 对于 BashTool 或文件读取产生的大量文本输出，采用启发式截断。通常只保留前 100 行和后 100 行（包含错误堆栈），中间部分用占位符替换，不消耗模型算力。

就地摘要 (In-place Summarization)： 当触发门限时，系统调用内置的 SummarizeTool，将早期的数十轮试错对话输入给模型生成短摘要，并在上下文中直接替换掉这些原始历史节点。

落盘换页 (State Eviction to Disk)： 对于无法继续压缩的长任务历史，系统将其序列化为 Markdown 文件写入本地硬盘（.claude/ 目录），当前上下文中仅保留一段文件路径指针，需要时通过 GrepTool 查阅。

7. 底层存储放弃数据库，转向 JSONL

提问： 源码中没有使用数据库吗？JSONL 是怎么存工具调用这些代码化内容的？

解答：
是的，Claude Code 底层并未采用 SQLite、PostgreSQL 或任何专门的数据库系统。

文件系统即数据库： 它的短期记忆和会话历史依赖于 JSONL (JSON Lines) 文件；长期提炼记忆依赖于 Markdown 文本文件。

技术动机：

极速恢复与免疫锁表： JSONL 采用 Append-only 模式写入。多并发写入或进程意外中断时，最多丢失最后半行字符串，天然免疫传统数据库的锁表（Database Locked）和文件损坏。

Git 分支同构： 纯文本的配置文件存在于代码工作区中。开发者切换 Git 分支时，Agent 的记忆文件会自然随代码版本回滚，保持严格的上下文一致性。

人类可调试性： 开发者可直接使用文本编辑器打开并手动修正模型产生的错误记忆，无需编写 SQL。

结构化内容的存储： 针对工具调用（Tool Calling），JSONL 的每一行存储一个完全合法的 JSON 对象。这些对象严格匹配 LLM 原生 API 的 messages 数组结构。包含 role、content（内部嵌套 tool_use_id、name、input 参数字典）。由于每行独立，读取后通过 JSON.parse 即可无缝转换为 API Payload。

8. 将 JSONL 应用于现有框架的可行性

提问： Google ADK 用的是数据库，能改成支持 JSONL 吗？有没有必要改？解析工具是怎么做的？

解答：

可行性： 现代框架（如 ADK）底层高度抽象，完全可以通过编写自定义的 JsonlSessionService 类来替换默认的数据库 Service。

是否有必要：

建议替换（本地/边缘计算场景）： 若智能体作为单机守护进程运行，JSONL 方案可实现零环境依赖、实时无障碍的日志观测，并避免高并发写锁。

不建议替换（云原生/多租户场景）： 若智能体面向多用户高并发，运行在无状态的云端容器集群（如 K8s）中，则必须依赖专业的数据库服务来保证事务完整性和高可用性。

解析机制 (ORM 映射)： 自定义的 JsonlSessionService 需要实现双向解析：

序列化 (写入)： 拦截 ADK 产生的面向对象实例（如 UserMessage、ToolCallRequest），将其降维提取核心字段，转换为标准化字典，使用 json.dumps() 配合换行符以追加模式写入文本。

反序列化 (读取)： 按行读取文本，使用 try-catch 包裹 json.loads() 以兼容处理末行可能存在的文件损坏。随后利用工厂模式，根据字典内的字段特征（如 role、tool_call_id）重新实例化对应的 ADK 系统对象。

9. 源码中其他值得关注的工程细节

提问： 泄露的源码中还有哪些对智能体开发有启发的工程实现？

解答：

Auto Mode 静默权限分类器： 针对系统安全与免打扰的权衡，在主控制流外旁路挂载了一个轻量的 ML 分类器（Classifier）。用于静默放行所有无损/只读命令（如网络连通性测试、读日志），仅对修改、重启等高危指令执行人机交互阻断。

类型级别的遥测数据隐私隔离： 在代码层利用极其严格的 TypeScript 类型约束（如命名为 AnalyticsMetadata_I_VERIFIED_THIS_IS_NOT_CODE），从编译期强制隔离业务上下文与系统运行日志，防止埋点代码意外泄露用户敏感代码。

单体 React 终端 UI： 命令行界面并未采用简单的标准输出控制，而是引入了 React 和 Ink 框架构建。部分入口组件长达 5000 行，以支持在终端内渲染复杂的拓扑图、动态进度机和多维状态信息。

拒绝过度设计的单主控制流： 尽管包含多智能体调度，但主控流保持了线性的 while 循环状态机，避免了业内流行的过度网状化图节点（Graph-node）设计。通过把复杂度下沉到独立的工具（Tools）中，换取了系统极高的可追踪性和稳定性。
